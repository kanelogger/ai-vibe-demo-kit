# AI Coding Agent 成本与上下文工程：从会话习惯到多 Agent 编排

AI Coding Agent 的成本不只由模型单价决定。真正进入账单和等待时间的，是一整条工作链：重复上下文、模型路由、工具输出、无效往返、失败重试，以及多个 Agent 之间的重复读取。

可以把优化目标写成四项：

```text
更低成本 =
  更少重复上下文
+ 更合理的模型路由
+ 更精准的代码与资料检索
+ 更清晰的 Agent 分工
```

顺序很重要。先修会话习惯，再做模型路由；确认瓶颈后安装压缩或图谱工具；只有任务真正可拆时才引入多 Agent。反过来做，工具越多，固定开销越大。

> 文中的节省比例来自各工具项目的公开材料或原始笔记，不是本文复现实验结果。把它们当成待验证假设，不要当成跨仓库保证。

## 一、先看成本从哪里产生

一次 Agent 任务的实际成本至少包含六部分：

| 成本 | 典型来源 | 可控手段 |
| --- | --- | --- |
| 固定上下文 | 系统提示词、`AGENTS.md`、工具定义、常驻 Skill | 精简规则、按需加载 |
| 会话历史 | 多轮讨论、旧任务、重复确认 | 一个会话一个目标、`/new`、`/compact`、`/handoff` |
| 工作材料 | 代码、网页、PDF、日志、工具结果 | 精准引用、先提取再汇总、输出压缩 |
| 模型调用 | 所有任务都使用强模型 | 角色路由、分级升级 |
| 失败与重试 | 模糊需求、错误工具、窄验证、返工 | 一次说清、约束输出、证据驱动验证 |
| 协作开销 | 多 Agent 重复读取背景、汇总冲突 | 清晰边界、结构化交接、只并行独立任务 |

只盯输入 Token 会漏掉最贵的一项：**返工**。一个低价模型连续跑偏五轮，通常比一次把需求交给合适模型更贵。

因此，每项优化都应同时观察：

- 输入与输出 Token；
- 总费用；
- 工具调用次数；
- 重试次数；
- 从开始到可验收结果的时间；
- 人工纠偏次数。

## 二、第一层：先改使用习惯

### 1. 一个 Session 只处理一个目标

修 Bug、做重构、写文章、排查线上问题，应分别建立会话。换任务时使用 `/new`，不要让自动压缩替你管理边界。

长会话的问题不只是“快装不下”：

- 每轮重新携带更多历史；
- 旧约束与新需求互相干扰；
- 模型更难判断哪条决策仍有效；
- 一旦方向改变，前面的读取与讨论都变成沉没成本。

`/compact` 适合同一任务的续作；`/handoff` 适合一个阶段完成后的交接；`/new` 适合无关任务。

### 2. 第一条指令尽量一次说完整

高质量任务说明至少包含：

- 目标；
- 相关路径或入口；
- 明确非目标；
- 不能违反的约束；
- 可观察的验收方式；
- 期望输出格式。

四轮聊天式补充，意味着四次重组历史、四次重新判断状态，还可能引入互相矛盾的要求。首条指令完整，不代表写成长篇散文；它要求信息闭环。

### 3. 引用完整路径与必要范围

“看一下配置文件”会触发搜索、候选判断和额外读取；“读取 `src/server/config.ts:40-120`，检查重试配置”直接给出边界。

不要为了省搜索成本而把整个仓库塞进上下文。路径准确、范围窄、目标明确，三者要同时成立。

### 4. 指定输出契约

只需要结论时，明确要求：

```text
直接输出：问题、证据路径、修复建议。不要复述需求。
```

只需要机器消费时，要求稳定 JSON schema；只需要修改时，要求 diff 和验证结果。更短的输出减少输出 Token，也减少人工提取和再次追问。

### 5. CLI 优先，但不迷信 CLI

选择顺序可以是：

```text
已有专用工具 > 确定性 CLI/脚本 > 通用 MCP > 浏览器自动化
```

CLI 通常返回更紧凑、行为更确定；MCP 的价值在跨系统编排、结构化权限、内部业务能力和长期连接。私有数据源接入 Agent 时，MCP 往往比临时 shell 脚本更合适，因为认证和能力边界可以集中管理。

原则是选择最短、最可靠的数据路径，不是把所有 MCP 都卸掉。

**Web UI 是例外。** 当验收条件涉及布局、交互、登录状态或浏览器兼容性时，CLI 输出和单元测试无法证明真实页面可用。此时应使用 Agent 内置浏览器或 `BrowserSkill` 一类真实浏览器集成，打开实际页面、走完用户路径并观察结果。它会增加一部分工具上下文，但能避免“测试通过、界面不可用”的假完成。

### 6. 主动压缩，而不是等溢出

自动压缩解决容量问题，不负责理解任务阶段。以下节点适合主动 `/compact` 或 `/handoff`：

- 设计决策已经收敛；
- 一个实现阶段完成；
- 大量探索记录不再影响后续；
- 会话需要交给另一个人或 Agent；
- 当前目标不变，但下一阶段只需要少量状态。

压缩时给出焦点，避免临时探索在摘要里获得过高权重。

### 7. 稳定公共前缀，保护 Prompt Cache

当模型提供商支持 Prompt Cache 时，跨请求重复且稳定的提示词前缀通常更容易复用缓存。它不会减少上下文本身，但可能减少重复前缀的处理成本和延迟；具体计费与命中规则取决于提供商。

可执行的做法：

- 把稳定的系统指令、项目约束和工具定义放在前部；
- 把当前任务、时间、日志和临时材料放在后部；
- 不要在公共前缀前插入时间戳、随机 ID 或实时状态；
- 不为纯格式偏好频繁重排 `AGENTS.md`、Skill 和工具定义；
- 通过提供商用量明细或 Agent 统计观察缓存读取量，不凭感觉判断命中。

缓存不能让无关上下文变得免费。过时规则和低频工具仍应删除或按需加载；稳定前缀只优化“必须重复的内容”。

## 三、第二层：按任务做模型路由

模型路由应落到角色、Skill 或 Agent 配置里，不能只存在于操作者脑中。

### 典型分工

| 任务 | 推荐档位 | 原因 |
| --- | --- | --- |
| 架构设计 | 强模型 | 长链路推理、权衡和风险判断 |
| 复杂 Bug 定位 | 强模型 | 多步假设与证据验证 |
| Code Review | 中高档或强模型 | 需要语义理解与反例构造 |
| 常规实现 | 中档模型 | 需要读写代码，但模式相对稳定 |
| 单元测试补齐 | 中低档模型 | 现有测试风格可复用时较模板化 |
| 提交信息、格式修复 | 低价模型 | 输出短、结构稳定 |
| 批量分类与摘要 | 低价或 Batch | 规模大、单项风险低 |

### 使用升级链，而不是一开始就上最贵模型

```text
低价模型分类或摘要
  ↓ 发现复杂度或高风险
中档模型实现
  ↓ 出现跨模块推理、证据冲突或难定位故障
强模型分析 / Review
```

升级条件必须明确，例如：

- 影响公开 API；
- 修改超过两个模块；
- 两轮后仍无法复现；
- 测试与实现证据冲突；
- 涉及并发、数据丢失、权限或迁移。

没有升级条件的“先用便宜模型”容易变成低价但高返工。

### 把路由写进执行单元

如果当前 Agent 平台支持 Skill 或 Agent 级模型配置，可将固定流程绑定到对应档位。平台字段并不通用，应以当前运行时 schema 为准；不要把某个平台的 frontmatter 复制到所有工具。

更稳定的设计是使用语义角色：Planner、Implementer、Reviewer、Mechanical Worker，再在配置中映射具体模型。模型更新时只改映射，不改所有工作流。

## 四、第三层：按瓶颈选工具

工具可以分成三类：压命令输出、压模型回复、压进入上下文的材料。第四类代码图谱工具解决“读哪里”，并不直接压缩文本。

### 1. RTK：压缩终端命令输出

RTK 过滤 ANSI、进度条、重复告警、注释和空行，减少命令结果进入上下文的体积。

```sh
# macOS
brew install rtk

# Linux / WSL
curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/master/install.sh | sh

# 按 Agent 初始化
rtk init -g
rtk init -g --codex
rtk init -g --gemini
rtk init -g --agent cursor
rtk init -g --agent omp
```

验证与观察：

```sh
rtk gain
rtk gain --history
rtk discover
```

它最适合测试、Git、构建和搜索这类高频且噪声多的命令。压缩后仍需保留退出状态和关键错误；如果过滤器隐藏了诊断信息，使用原始命令复查该次失败。

### 2. Caveman：压缩 Agent 回复

[Caveman](https://github.com/juliusbrussee/caveman) 作用于输出端，提供不同压缩档位。原始笔记采用支持 OMP 的 Fork：

```sh
git clone https://github.com/studyzy/caveman
cd caveman && ./install.sh
```

安装后通过 `/caveman` 启用，使用 `stop caveman` 关闭。

它适合人只需要简洁结论的会话，不适合依赖完整推理记录、长篇文稿或严格机器格式的任务。开启前先检查当前版本与 Agent 的兼容性。

### 3. headroom：压缩进入上下文的多类内容

headroom 面向文件、工具返回和会话历史，原始材料还提到可选的缓存对齐、记忆和代码图谱能力。

```sh
pip install "headroom-ai[all]"
headroom wrap omp
headroom wrap omp --memory --code-graph
```

也可安装 MCP 模式：

```sh
headroom mcp install
```

这类代理层工具改变了 Agent 实际看到的材料。上线前应测试：引用能否回取、代码块是否保持完整、错误日志是否被误压、敏感数据存储在哪里。

### 4. context-mode：压缩 MCP 工具结果并维持会话连续性

context-mode 重点处理体积很大的 MCP 返回，例如浏览器快照，并使用本地存储维持 `/compact` 前后的可检索状态。

```sh
npm install -g context-mode
```

原始笔记给出的诊断入口：

```text
/context-mode:ctx-doctor
/context-mode:ctx-stats
/context-mode:ctx-insight
```

它适合浏览器、数据库和文档工具频繁返回大块内容的工作流。若瓶颈来自糟糕的会话边界，安装它只会让长会话晚一点爆满。

### 5. Graphify：用静态代码图谱缩小读取范围

Graphify 使用 Tree-sitter 生成项目图谱，让 Agent 先定位入口、符号和关系，再读取具体源码。

```sh
uv tool install graphifyy
# 或
pipx install graphifyy

graphify install --platform omp
# 或
graphify omp install
```

之后在 OMP 中按当前插件说明执行图谱扫描。适合入口难找、语言较多或模块关系复杂的仓库；小项目可能不值得承担索引维护成本。

### 6. CodeGraph：持久化代码图数据库

CodeGraph 通过 MCP 暴露入口定位、调用追踪和影响分析能力，可选择 Neo4j 或 KuzuDB 等持久化后端。

```sh
npm i -g @colbymchenry/codegraph
cd your-project
codegraph init -i
```

原始笔记中的 MCP 配置：

```json
{
  "mcpServers": {
    "codegraph": {
      "type": "stdio",
      "command": "codegraph",
      "args": ["serve", "--mcp"]
    }
  }
}
```

典型工具包括：

- `codegraph_context`：找入口；
- `codegraph_trace`：追调用路径；
- `codegraph_impact`：重构前评估影响。

图数据库返回的是高密度关系数据。它可以减少盲目读文件，也可能在长会话中积累新的密集上下文。应同时测量“少读了多少文件”和“图查询结果残留了多少 Token”。

### 工具选择表

| 症状 | 先做什么 | 再考虑什么 |
| --- | --- | --- |
| 测试与 Git 输出过长 | 限定命令范围、使用 RTK | 自定义过滤规则 |
| Agent 回复太长 | 明确输出契约 | Caveman |
| MCP 快照巨大 | 缩小查询或元素范围 | context-mode |
| 多类材料反复进上下文 | 改会话边界与提取流程 | headroom |
| Agent 不知道该读哪些文件 | 给入口、用 LSP/代码搜索 | Graphify 或 CodeGraph |
| 仓库很小、调用关系简单 | 保持原工具链 | 通常不需要图谱 |

先有可观测瓶颈，再装工具。低频 Skill、Agent、MCP 和插件应禁用或按需加载，避免固定工具定义长期占用上下文。

## 五、第四层：多 Agent 只在边界清晰时更省

单 Agent 会话常把规划、代码阅读、实现、测试和 Review 混在一起。职责越多，历史越长，所有步骤都被迫携带同一批上下文。

多 Agent 的潜在收益来自两点：

1. 每个 Worker 只看当前步骤需要的材料；
2. 不同角色可以使用不同模型，并对独立任务并行执行。

但拆分也有成本：启动提示词、重复背景、数据交接、结果汇总和冲突处理。如果每个 Agent 都要读同一批文件，多拆只会更贵。

### 四种手段不要混用

| 手段 | 解决什么 | 历史如何处理 | 代码是否隔离 | 适用场景 |
| --- | --- | --- | --- | --- |
| `/new` | 换任务 | 新会话 | 同一工作区 | 无关需求 |
| `/compact` | 历史过长 | 旧历史变摘要 | 同一工作区 | 同一长任务 |
| subagent | 职责拆分 | 独立上下文 | 默认未必隔离 | 搜索、分析、实现、验证 |
| worktree | 并发改动冲突 | 不是重点 | 独立 Git worktree | 多个独立代码任务 |

一句话：`/new` 管任务边界，`/compact` 管历史长度，subagent 管职责，worktree 管代码并发。

### Orchestrator–Worker 模式

```text
Orchestrator
  ├── 明确目标、依赖与验收标准
  ├── 为每个 Worker 裁剪上下文
  ├── 决定并行与串行关系
  └── 汇总证据并作最终决策

Worker
  ├── 一次只完成一个边界明确的任务
  ├── 只读取必要文件或上一步结构化结果
  ├── 输出可验证产物
  └── 完成后释放上下文
```

Orchestrator 不应只是“转发用户需求”。它必须在派工前定义接口：输入路径、允许修改范围、输出 schema、验收方式和依赖关系。

### 通过文件传递状态，不通过完整会话历史

上下文隔离后，Agent 之间最稳定的桥梁是结构化外部文件：

```text
Worker A
  → 输出 .agent/findings.json
Worker B
  → 只读取 findings.json 与相关源码
  → 输出 .agent/fix-result.json
Worker C
  → 读取 fix-result.json 与现有测试
  → 输出测试结果
```

示例发现文件：

```json
{
  "task": "locate-order-bug",
  "status": "completed",
  "findings": [
    {
      "file": "src/api/order.go",
      "line": 142,
      "issue": "错误路径未释放 inventory lock",
      "severity": "high"
    }
  ],
  "next_step": "fix-bug",
  "context_needed": [
    "src/api/order.go:120-165",
    "src/model/inventory.go:30-55"
  ]
}
```

结构化结果的优势：

- 下游只读取需要的字段；
- Orchestrator 可检查缺失项和状态；
- 失败后能从最近产物继续；
- 不需要把 Worker 的完整历史复制给下一个 Worker。

### 用进度文件记录依赖

```json
{
  "task_id": "fix-order-bug",
  "steps": [
    {
      "id": "locate",
      "status": "completed",
      "output": ".agent/findings.json"
    },
    {
      "id": "fix",
      "status": "in_progress",
      "depends_on": ["locate"]
    },
    {
      "id": "test",
      "status": "pending",
      "depends_on": ["fix"]
    }
  ]
}
```

状态文件只记录协作所需事实，不要把它写成另一份会话日志。任务完成后，按仓库约定归档或删除临时 `.agent/` 目录；清理前先确认其中没有仍需审阅的证据。

### 只并行真正独立的任务

适合并行：

- 不同模块、修改文件不重叠的 Bug；
- 同一份稳定 diff 上的测试缺口分析与变更说明；
- 多个互不依赖的资料收集任务；
- 两种方案的隔离实验。

必须串行：

- 先定位 Bug，才能确定如何修复；
- 测试需要读取最终实现；
- 多个 Worker 修改同一文件或共享状态；
- 下游输入 schema 尚未确定。

并行减少的是墙上时间，不会自动减少总 Token。若两个 Worker 重复读取同一背景，总费用可能上升。

### 一个端到端例子

任务：统一一个 Go 项目的 API 错误处理，并补测试和变更说明。

```text
阶段 0：Orchestrator
  - 明确 Error Wrapper 契约
  - 列出候选文件与依赖
  - 定义 findings / fix / test 输出 schema

阶段 1：并行分析
  - Worker A 扫描非标准错误处理
  - Worker B 评估现有测试缺口

阶段 2：实现
  - 按模块或互不重叠文件分配 Worker
  - 每个 Worker 只改自己负责的范围

阶段 3：验证
  - 基于最终实现补测试
  - 运行相关测试与实际 smoke test

阶段 4：并行汇总
  - Reviewer 根据需求、diff、测试和日志找反例
  - Writer 根据同一证据生成变更说明

阶段 5：Orchestrator 验收
  - 检查每项交付与证据
  - 处理冲突
  - 清理临时协作文件
```

这里真正节省成本的部分，是每个 Worker 的输入被裁剪，且 Reviewer 与 Writer 共享的是最终证据，不是全程历史。

## 六、分阶段落地

### 今天就能做

- 一个 Session 只处理一个目标；
- 换任务用 `/new`，长任务按阶段 `/compact` 或 `/handoff`；
- 首条指令一次给全目标、边界与验收；
- 引用完整路径和必要范围；
- 指定输出格式，减少废话和二次提取；
- 清点常驻 Skill、MCP、Agent 与插件；
- 能用现有专用工具或确定性 CLI 时，不新增通用中间层。

### 这周能做

- 按 Planner、Implementer、Reviewer、Mechanical Worker 做模型分档；
- 为升级到强模型定义触发条件；
- 安装 RTK，先观察测试、Git 和构建输出的变化；
- 评估 Agent 最常在哪一步盲目读文件；
- 选择 Graphify 或 CodeGraph 做一个真实仓库对照实验，而不是同时安装两个。

### 这个月能做

- 建立 Token、费用、重试、工具调用和交付时间的基线；
- 评估 headroom 或 context-mode 是否解决了已观测瓶颈；
- 为复杂任务定义 Orchestrator–Worker 的输入输出 schema；
- 用 worktree 隔离真正独立的并发改动；
- 把高复用的规划、实现、验证和 Review 流程沉淀为 Skill；
- 清理没有可观测收益的工具。

## 七、最终检查表

优化前先问：

1. 当前瓶颈是输入、输出、检索、模型单价、返工，还是等待时间？
2. 能否通过更清楚的任务边界直接解决？
3. 新工具会增加多少固定上下文和维护面？
4. 多 Agent 是否会重复读取同一批背景？
5. 省下的 Token 是否换来了更多失败或人工纠偏？
6. 是否有基线和对照数据证明改动有效？

成本工程的目标不是把每轮 Token 压到最低，而是用更少的总成本拿到可验收结果。清晰边界、正确模型和真实证据，通常比任何“物理外挂”更先产生收益。
