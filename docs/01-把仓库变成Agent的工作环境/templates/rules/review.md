# Review Rules

独立 Review 的产出契约。Reviewer 使用不同模型或不同 Agent，材料只给原始需求、生效规格、最终差异、验证结果和已知风险，不给完整对话历史（见第 2 章「独立 Review」）。本文件约束 Reviewer 怎么报告，不约束它找什么。

## 严重度语义

每条发现必须标注严重度，并写出人话含义，禁止只给裸 `P1`/`P2`/`P3`：

- `[P1 阻断]`：必须修复后才能合并；
- `[P2 非阻断]`：建议修改，不阻断合并；
- `[P3 可选]`：细节打磨、理论边界，或已明确交由 CI 覆盖的事项。

英文项目使用 `[P1 blocking]` / `[P2 non-blocking]` / `[P3 nit]`。

## 证据门禁

- 每条 `[P1 阻断]` 必须引用二者之一：具体失败场景（触发输入或状态，以及产生的错误行为），或本文件/项目规则中的具体条目。
- 两者都引用不了的发现，最高只能是 `[P2 非阻断]`；需要不常见前置条件才成立的推测性风险，最高只能是 `[P3 可选]`。
- 禁止重复报告当前差异中已解决的发现。

## 审查边界

- 只报告当前差异中你确信真实存在的问题；不确认的不报。
- 不为发现数量设上限：一次审查里出现的真实缺陷都应报告，不推迟到下一轮。
- 不重复审查无关代码；已明确排除的范围不报。
- 区分真实缺陷、偏好建议和无证据推测，三者不混在同一条发现里。
- 不要求本地跑满组合矩阵；因环境不具备而未覆盖的组合，作者已说明或已交 CI 时最高只能是 `[P3 可选]`，不得判为 `[P1 阻断]`。

## 过度工程

- 拒绝过度设计：偏好解决问题的最小实现。
- 标出推测性抽象、无人使用的灵活性或配置、不可能发生场景的错误处理，以及可以复用或扩展现有命令时新增的命令。
- 改动必须聚焦：每一行改动都应能追溯到本次声明的目标；标出无关的顺手改动。
