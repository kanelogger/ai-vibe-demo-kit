# AGENTS.md 自动化操作手册

本手册用于新建、重构和维护用户级与项目级 Agent 规则文件。Agent 负责调查、分类、起草、审阅、写入和验证；用户只负责批准用户级规则变更，以及裁决无法由证据解决的真实偏好冲突。

本手册与同目录下的两个模板配套使用：

- `AGENTS-用户级模板.md`
- `AGENTS-项目级模板.md`

模板定义内容边界，本手册定义执行流程。Agent 不得把模板说明、示例或占位符直接写入最终文件。

## 1. 适用范围

本手册适用于以下任务：

- 第一次创建用户级或项目级规则文件。
- 将现有规则迁移到用户级、项目级、局部规则、独立文档或 Skill。
- 精简重复、冲突、过时或可由仓库直接发现的规则。
- 根据多次独立会话证据维护项目级规则。
- 验证规则文件是否在新会话中按预期加载。

本手册不授权 Agent：

- 根据单次会话自动改写用户级规则。
- 未经用户批准写入任何目标文件。
- 创建未获批准的局部规则、独立文档、Skill 或符号链接。
- 提交、推送或发布改动。
- 联网补充项目事实。

## 2. 角色与人工门禁

### 协调 Agent

负责读取资料、建立规则来源图、生成草稿、组织审阅、执行获批写入并汇总结果。

### Reviewer Agent

在独立上下文中审阅草稿。Reviewer Agent 只接收事实来源、现有文件和草稿，不接收协调 Agent 的起草理由或结论。

### Verifier Agent

在写入后的全新上下文中验证规则加载结果。Verifier Agent 不接收旧对话、模板内容或获批草稿。

### 用户

只处理以下事项：

1. 批准内容固定的审阅包。
2. 裁决无法通过作用域、优先级或现有证据解决的个人偏好冲突。

用户级规则影响所有项目。Agent 即使没有发现问题，也不得跳过批准门。

如果平台不支持独立 Agent：

- 协调 Agent可以完成确定性检查，但必须把语义审阅标记为「未独立审阅」。
- 用户应在新会话中执行 Reviewer 或 Verifier 提示词。
- 原会话中的自检不能冒充独立审阅或新上下文验证。

## 3. 文件发现规则

Agent 必须根据当前环境发现实际路径，不要求用户替换 `{user}` 或 `{project}`。

### 输入文件

默认从本手册所在目录读取：

```text
AGENTS-用户级模板.md
AGENTS-项目级模板.md
```

### 目标文件

- 用户级目标：由当前 Agent 工具和启动上下文确定，例如 `~/.codex/AGENTS.md`、`~/AGENTS.md` 或 `~/.claude/CLAUDE.md`。
- 项目级目标：当前仓库根目录的 `AGENTS.md`。

### 发现要求

1. 确认当前仓库根目录。
2. 确认两个模板存在且可读。
3. 确认当前环境实际加载的用户级规则路径。
4. 读取现有用户级目标及其直接引用的规则文件。
5. 读取现有项目级目标，以及平台已加载或该文件直接引用的局部规则入口。
6. 不复制引用文件全文，不全仓库盲目搜索规则文件。
7. 如果多个用户级候选路径都可能生效且无法判定，列出候选路径并停止写入流程。

## 4. 快速开始

在目标仓库的新会话中发送：

```text
按照 `AGENTS-自动化操作手册.md` 执行 AGENTS.md 初始化或重构。
以当前仓库为项目根目录。完成调查、起草和独立审阅，生成审阅包后停止；未经批准不要修改任何文件。
```

Agent 应执行第 5～10 节，然后停在「人工批准门」。用户不需要复制模板中的长提示词，也不需要手工填写路径。

批准时发送：

```text
批准审阅包 `<审阅包 ID>`。严格写入该审阅包中的两份草稿，不得重新生成或润色内容。继续执行安全写入、写入后检查和新上下文验证。
```

如果审阅包包含待决定冲突，用户应在批准消息中同时给出选择。任何草稿修改都会产生新的审阅包 ID，原批准随即失效。

## 5. 阶段一：预检与来源快照

本阶段只读，不修改文件。

### 5.1 读取资料

协调 Agent 依次读取：

1. 本手册和两个参考模板。
2. 当前环境实际使用的用户级规则文件。
3. 用户级文件直接引用的通用规则。
4. 当前项目已有的根目录 `AGENTS.md`。
5. 根文件直接引用或平台已经加载的局部规则、参考文档和 Skill 入口。
6. 项目根目录中的构建、测试、包管理和配置入口，只用于确认稳定事实是否可直接发现。

### 5.2 建立规则来源图

规则来源图至少包含：

| 来源 | 作用域 | 是否自动加载 | 直接引用 | 当前状态 |
| --- | --- | --- | --- | --- |
| 用户级目标 | 所有项目 | 是／否／待确认 | 路径列表 | 存在／缺失 |
| 项目根文件 | 当前仓库 | 是／否／待确认 | 路径列表 | 存在／缺失 |
| 局部规则 | 指定目录 | 是／否／待确认 | 路径列表 | 存在／缺失 |
| 独立文档或 Skill | 按需 | 否 | 触发入口 | 存在／缺失 |

### 5.3 保存源快照

对每个现有目标记录：

- 绝对路径。
- 是否存在。
- SHA-256。
- 文件大小。
- 修改时间。

不存在的文件以 `MISSING` 记录。源快照用于在写入前检测并发修改，不能用 Git 版本代替当前工作区内容。

### 5.4 停止条件

出现以下情况时，不进入起草阶段：

- 无法确认当前仓库根目录。
- 模板缺失或不可读。
- 无法唯一确定用户级目标。
- 现有规则引用形成无法判断的循环或指向不可读取的关键文件。
- 发现疑似凭据、令牌或私钥，需要先确定是否应从规则文件中移除。

协调 Agent 应完成所有仍可执行的只读调查，再报告阻塞项。

## 6. 阶段二：规则分类

协调 Agent 必须为现有规则逐条确定去向，不得静默删除。

### 6.1 分类结果

每条规则只能进入以下一种主要分类：

| 处理方式 | 含义 |
| --- | --- |
| 保留 | 内容和作用域正确，继续保留 |
| 重写 | 保留原意，修复歧义、重复或不可执行表达 |
| 移到用户级 | 跨项目、长期稳定的个人偏好 |
| 移到项目级 | 当前仓库全局适用且无法可靠推导的稳定约束 |
| 下沉到局部规则 | 只适用于特定目录或包 |
| 下沉到文档或 Skill | 有明确触发条件的固定流程或按需知识 |
| 删除 | 重复、过时、空泛、可直接发现或只有单次失败依据 |
| 待用户决定 | 真实偏好冲突，且证据和优先级都无法消解 |

分类表至少包含：

```text
现有内容｜来源｜处理方式｜目标位置｜证据｜理由
```

### 6.2 用户级纳入标准

用户级草稿只保留：

- 跨多个项目都适用的个人偏好。
- 预计长期稳定的质量标准和协作方式。
- 通用验证要求、安全边界和工具偏好。
- Agent 无法从当前仓库可靠推导的内容。
- 值得在每次会话中持续占用注意力的规则。

不得放入项目专属路径、命令、技术栈、模块、领域术语或当前实现状态。

### 6.3 项目级纳入标准

项目级草稿只保留：

- 一句话项目定位。
- 默认工具无法推导的非标准命令。
- 仓库级安全或数据完整性约束。
- 稳定且容易误解的领域概念。
- 指向局部规则、独立文档或 Skill 的按需入口。
- 有至少两次独立会话证据支持的普通规则。

可从代码、配置、Schema、包管理文件或标准目录结构可靠发现的事实不进入项目根文件。

### 6.4 冲突处理

按以下顺序消解冲突：

1. 系统和工具的强制约束。
2. 用户当前任务中的明确要求。
3. 作用域更窄的有效项目规则。
4. 现有用户级偏好。
5. 证据充分且较新的维护规则。

只有涉及个人取舍、且以上顺序不能得出唯一结论时，才列入「待用户决定」。多个冲突应一次性集中列出，不要逐个打断流程。

## 7. 阶段三：生成完整草稿

协调 Agent 生成两份完整文件内容。

### 7.1 通用要求

两份草稿必须：

- 没有 `【】`、`{user}`、`{project}` 等未解析占位符。
- 没有模板说明、示例内容、空章节和代码围栏。
- 保留仍然有效的现有规则及外部引用。
- 不复制外部规则文件全文。
- 不新增没有来源的事实、命令、路径、限制或工作流。
- 使用可执行、可验证、作用域明确的表达。
- 没有重复或互相冲突的规则。

### 7.2 用户级草稿

用户级草稿不得包含：

- 当前项目名称和专属路径。
- 当前项目的包管理器、构建命令或测试命令。
- 只适用于某种语言、框架或目录的项目规则。
- 根据本次任务临时推断的个人偏好。

用户级草稿应明确：只有用户明确要求时，Agent 才能提出或执行后续修改。

### 7.3 项目级草稿

项目级草稿必须保持小而聚焦：

- 优先保留「项目」和「工具与验证」。
- 没有真实内容的章节直接删除。
- 按需资料使用相对路径。
- 不重复用户级沟通偏好、工程原则或通用安全规则。
- 不记录容易过时的模块、函数和实时文件位置。

本阶段不得创建局部规则、独立文档、Skill、符号链接或其他辅助文件。需要下沉的内容只列为建议，等待单独批准。

## 8. 阶段四：确定性检查

协调 Agent 对草稿运行以下检查。

### 8.1 结构检查

- 标题层级有效。
- 没有空章节、空列表项和模板外围说明。
- 没有未解析占位符。
- 文件末尾和代码字面量保持有效。

### 8.2 作用域检查

- 用户级草稿没有项目专属路径、命令、技术栈和领域术语。
- 项目级草稿没有重复用户级偏好。
- 局部规则没有被提升到项目根文件。
- 可发现事实没有被固化为常驻规则。

### 8.3 完整性检查

- 每条现有规则在分类表中都有明确去向。
- 删除项都有具体理由。
- 外部引用仍然存在，或已明确标记为失效。
- 两份草稿之间没有含义相同的重复规则。

### 8.4 冲突与风险检查

- 同一作用域内没有互相否定的要求。
- 不同作用域的规则具有可判断的优先级。
- 没有允许未经批准删除、覆盖、提交、推送或发布的新增规则。
- 没有凭据、令牌、私钥、内部账号或其他不应进入项目文件的信息。
- 没有「保持高质量」「遵循最佳实践」等无法验收的空泛要求。

确定性检查可以发现明确错误，但不能代替语义审阅。

## 9. 阶段五：独立语义审阅

协调 Agent 应调用独立 Reviewer Agent。Reviewer Agent 不修改文件，也不重新设计用户偏好。

### 9.1 Reviewer 输入

- 两个参考模板。
- 现有用户级和项目级文件。
- 规则分类表。
- 两份完整草稿。
- 确定性检查结果。

不要提供协调 Agent 的内部推理、偏好或结论。

### 9.2 Reviewer 检查项

1. 是否静默删除了仍有效的规则。
2. 是否把项目事实错误提升到用户级。
3. 是否把通用偏好重复写入项目级。
4. 是否新增了没有证据的事实或限制。
5. 是否遗漏安全边界、失败处理或必要例外。
6. 是否存在语义重复、冲突、模糊对象或不可执行要求。
7. 是否错误处理了直接引用、代码字面量、路径和命令。
8. 是否存在需要用户裁决但被 Agent 擅自选择的偏好冲突。

### 9.3 Reviewer 输出

Reviewer 按以下级别报告：

- `阻塞`：批准前必须修复。
- `警告`：可能影响作用域、事实或长期维护，需要明确处理。
- `建议`：不影响正确性的精简建议。

每项必须包含草稿位置、对应来源和修改理由。没有证据的主观偏好不构成问题。

协调 Agent 修复确认的问题后，必须重新执行确定性检查并重新计算草稿哈希。不得沿用修改前的审阅结果。

## 10. 阶段六：生成审阅包

审阅包是人工批准的唯一对象。协调 Agent 依次输出：

1. **审阅包 ID**。
2. **路径与源快照**。
3. **规则分类表**。
4. **用户级草稿**。
5. **项目级草稿**。
6. **相对现有文件的两份 diff**。
7. **确定性检查结果**。
8. **Reviewer 结果及处理情况**。
9. **需要用户决定**。
10. **批准后将执行的写入和验证动作**。

两份草稿使用独立 Markdown 代码围栏展示，并明确说明代码围栏不属于文件内容。

审阅包 ID 使用以下内容的 SHA-256：

```text
<用户级草稿 UTF-8 内容>
---PROJECT---
<项目级草稿 UTF-8 内容>
```

同时单独报告两份草稿的 SHA-256。任何字符变化都会产生新的审阅包 ID。

输出审阅包后，协调 Agent 必须停止。以下表达不能视为批准：

- 「看起来可以」。
- 「继续看看」。
- 「按建议处理」。
- 没有审阅包 ID 的模糊确认。

## 11. 人工批准门

用户只需要重点确认：

- 用户级草稿是否准确表达长期个人偏好。
- 用户级草稿是否包含项目专属内容。
- Agent 是否删除或改变了仍需保留的独特规则。
- 「待用户决定」中的冲突应选择哪个版本。

用户提出任何修改后，协调 Agent 必须生成新的完整草稿、检查结果、diff 和审阅包 ID。旧审阅包不能写入。

## 12. 阶段七：安全写入

只有收到包含有效审阅包 ID 的明确批准后，协调 Agent 才能写入。

### 12.1 写入前检查

1. 重新读取两个目标文件。
2. 将当前 SHA-256 与审阅包中的源快照比较。
3. 重新计算获批草稿的 SHA-256。
4. 确认草稿哈希与审阅包一致。
5. 确认没有新的未解决冲突。

任一目标文件在审阅后发生变化时，立即停止。不得覆盖并发修改，也不得把旧草稿自动合并到新内容中。Agent 应重新调查并生成新审阅包。

### 12.2 创建备份

写入前备份每个已存在的目标文件：

- 备份名包含 UTC 时间戳和原文件名。
- 项目级备份不得放在项目工作树中。
- 优先使用工具提供的持久化备份或产物目录；否则使用用户配置目录中的专用备份目录。
- 备份后计算 SHA-256，并与源快照比较。
- 任一备份失败时，不写入任何目标文件。

不要使用 `git reset`、`git checkout` 或其他会覆盖工作区内容的命令代替备份。

### 12.3 写入目标

1. 写入获批的用户级草稿。
2. 写入获批的项目级草稿。
3. 不重新生成、整理或格式化草稿。
4. 在工具支持时使用同文件系统上的原子替换。
5. 保留原文件权限；新文件使用普通文本文件权限。
6. 不修改目标和备份之外的文件。

### 12.4 读回验证

写入后立即重新读取两个目标：

- 计算 SHA-256。
- 与获批草稿哈希逐一比较。
- 检查文件路径、大小和权限。
- 重新执行第 8 节的确定性检查。

如果内容哈希不一致或确定性检查出现阻塞项，且目标文件没有发生新的并发变化，Agent 应从备份恢复两个目标并验证恢复后的哈希。存在并发变化时，停止自动恢复并报告实际状态。

## 13. 阶段八：新上下文验证

确定性检查通过后，使用全新的 Verifier Agent 或新会话验证。不得使用起草和写入所在的原上下文冒充新会话。

向 Verifier Agent 发送：

```text
这是一次只读的 AGENTS.md 新上下文验收。
只依据本次会话启动时自动加载的规则完成以下检查：

1. 用一句话说明当前仓库的用途。
2. 分别列出当前适用的用户级规则类型和项目级规则类型，不复述完整规则。
3. 说明当前项目认可的最小验证命令；规则没有提供时明确写“未提供”。
4. 报告是否发现模板占位符、模板说明、空章节、重复规则或无法消解的冲突。
5. 报告本次会话自动加载的规则来源；环境没有提供来源信息时明确写“无法确认”。

不要修改文件，不要打开参考模板或旧草稿。
```

### 验收标准

- 仓库用途与项目级文件一致。
- 用户级内容只体现跨项目稳定偏好。
- 项目级内容只体现当前仓库约束。
- 最小验证命令与项目级文件一致，或正确报告未提供。
- 没有引用模板占位符、模板说明或已删除规则。
- 没有报告无法消解的规则冲突。

Verifier Agent 无法确认自动加载来源时，只能把加载验证标记为「未证明」，不能推断为通过。

新上下文语义验证失败时，不自动覆盖或回滚文件。协调 Agent 应报告失败项、静态检查结果和备份位置，等待用户决定修正或恢复。确定性的内容哈希失败仍按第 12.4 节处理。

## 14. 阶段九：最终报告

协调 Agent 最终报告：

- 实际用户级和项目级写入路径。
- 审阅包 ID。
- 写入前后的 SHA-256。
- 备份路径和备份 SHA-256。
- 两份实际 diff；项目位于 Git 仓库时同时给出项目级 Git diff。
- 确定性检查结果。
- Reviewer Agent 的审阅结果。
- Verifier Agent 的新上下文验收结果。
- 是否发生恢复，以及恢复后的状态。
- 仍需用户处理的事项；没有则写「无」。

报告不得声称未执行的检查已经通过。

## 15. 失败与恢复规则

| 失败阶段 | Agent 动作 |
| --- | --- |
| 路径无法唯一确定 | 完成可执行的只读调查，列出候选路径并停止 |
| 源文件在批准后变化 | 不写入，重新生成审阅包 |
| 草稿哈希与审阅包不一致 | 不写入，重新生成审阅包 |
| 备份失败 | 不写入任何目标 |
| 第一个目标写入成功、第二个失败 | 在没有并发变化时恢复第一个目标 |
| 写入后内容哈希不一致 | 在没有并发变化时恢复两个目标 |
| 确定性检查出现阻塞项 | 在没有并发变化时恢复两个目标 |
| 独立语义验证失败 | 保留现场和备份，报告后等待用户决定 |
| 无法启动独立 Reviewer 或 Verifier | 标记为未独立验证，不得声称通过 |

任何恢复动作都必须先确认目标仍是本轮 Agent 写入的版本，避免覆盖用户或其他进程的新改动。

## 16. 后续维护

### 16.1 启动维护审计

发送：

```text
按照 `inbox//技术/agents/AGENTS-自动化操作手册.md` 对当前用户级和项目级规则做只读维护审计。
收集候选规则及证据，最多提出 5 条独立语义变更。没有充分证据时明确建议不修改。生成审阅包后停止。
```

维护仍需经过同一套独立审阅、人工批准、安全写入和新上下文验证。

### 16.2 独立会话证据

普通项目级规则至少需要两次独立会话证据。有效证据包括：

- 可访问的不同会话记录或会话 ID。
- 两个独立任务中出现的同类错误或重复探索。
- 两个独立 issue、评审记录或可复现失败产物。
- 用户在不同会话中针对同一问题作出的同类纠正。

同一会话中的多次失败只算一次证据。转述、猜测和无法定位来源的描述不算证据。

证据表至少包含：

```text
候选规则｜现象或损失｜证据一｜证据二｜是否可由仓库发现｜建议去向
```

无法访问两次独立证据时，Agent 只能把内容列为候选，不得声称纳入标准已经满足。

安全和数据完整性规则可以不满足两次证据，但必须说明具体风险、受影响对象和为何需要常驻。

### 16.3 每轮五处的定义

「一处」指一条独立语义规则的新增、删除、实质重写或迁移：

- 同一规则从根文件移到局部文件，计 1 处。
- 同一规则的纯排版调整，不计入语义变更。
- 一次修改产生两个独立义务，计 2 处。
- 合并两条重复规则，计 1 处。
- 初次创建或完整模板迁移不受五处限制，但必须作为一个完整迁移审阅包由用户批准。

普通维护每轮最多执行 5 处语义变更。超过部分保留为候选，不得静默拆分后连续写入多轮以绕过限制。

### 16.4 无证据时不修改

出现以下情况时，维护结果应为「不修改」：

- 没有新的独立证据。
- 候选信息可以从代码或配置可靠发现。
- 问题只发生在一次性任务中。
- 新规则与现有规则重复。
- 新规则需要用户偏好，但用户没有明确表达。
- 新增内容的常驻注意力成本高于可证明收益。

## 17. 修复已有问题文件

发送：

```text
按照 `AGENTS-自动化操作手册.md` 修复当前 AGENTS.md 规则体系。
先识别冲突、重复、错误分层、过时内容、可发现事实和应下沉流程；只把真正的个人偏好冲突交给我决定。
生成规则来源图、分类表、两份完整草稿、独立审阅结果和审阅包后停止，不修改文件。
```

Agent 可以自动完成：

- 识别能够由优先级和作用域消解的冲突。
- 提取用户级和项目级核心内容。
- 将其余规则归类为局部规则、独立文档、Skill 或删除候选。
- 设计精简的根文件和按需入口。
- 标记冗余、空泛、过时和可直接发现的内容。

Agent 不得在本轮创建建议的局部文件、独立文档或 Skill。需要实际下沉时，应单独展示文件清单和内容，经过用户批准后再执行。

## 19. 推荐执行边界

整个流程只保留一个强制人工批准门：两份完整草稿通过独立审阅之后、写入之前。

Agent 负责机械工作和证据检查；用户保留全局偏好的治理权。这样可以减少复制提示词、手工比对和重复验证，同时避免 Agent 因单次会话、自我审阅或过期快照而重写长期规则。
