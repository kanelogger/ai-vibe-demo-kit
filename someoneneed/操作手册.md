## 1. AGENTS.md 写作与维护

### 1.1 定位与硬预算

* AGENTS.md 是每次请求都会进入上下文的高优先级配置层，不是"完整项目说明书"。
* 指令预算：前沿推理模型约能稳定遵循 150–200 条指令；每个 Token 每次请求都加载。
* 理想形态：**小而聚焦，指向别处**——足够开始工作的上下文 + 面包屑式链接。

### 1.2 根文件只留底线

| 必留                   | 示例                         |
| -------------------- | -------------------------- |
| 一句话项目描述（角色型提示词）      | 这是一个用于无障碍数据可视化的 React 组件库。 |
| 包管理器（若非 npm）         | 本项目使用 pnpm workspaces。     |
| 非标准构建 / typecheck 命令 | —                          |

其余全部渐进式披露。

### 1.3 渐进式披露的四个出口

1. **独立文件**：语言约定 → `docs/TYPESCRIPT.md`，根文件只写一句"TypeScript 约定请参见 docs/TYPESCRIPT.md"（不用"始终/绝不"式语气）。
2. **嵌套引用**：docs 之间互相引用，构建可发现资源树（TYPESCRIPT.md → TESTING.md）。
3. **Skills**：只在需要时加载的工作流知识。
4. **Monorepo 子目录 AGENTS.md**：根级写仓库用途与共享工具；包级写包用途与技术栈。子目录文件与根级合并，注意每一层都不过载。

### 1.4 禁止事项

* 不要用 `/init` 或脚本自动生成——追求"全面"必然塞进大量易过时信息。
* 不重复 Agent 可以自己发现的信息：**具体文件路径、模块位置、当前实现细节**。记录能力而非结构："东西可能在哪儿" + 项目轮廓，让 Agent 按需探索。
* 领域概念（organization vs group 这类术语区别）比路径稳定，可记录，但点到为止。
* 不写冗余、模糊、"写出干净的代码"这类显而易见的内容。

### 1.5 实战经验：值得写进 AGENTS.md 的六条

1. 偏好"新增再替换"而非原地重写模块。
2. 引导自动化测试：有测试的项目，写明"实现功能的同时同步写测试，并用测试验证"。
3. 报告类输出（测试/分析/汇总报告）用 HTML 而非 Markdown，可引入 ECharts CDN。
4. AI 生成的 PRD 必须附一份"小孩都能看懂"的简报，防止 grill-me 式一路同意后产出读不懂的需求。
5. 主 Agent 的职责是分析、编排、验证；读大量代码、写代码、跑测试、批量修改一律派给 subagent。
6. 高频工具选择偏好（如浏览器操作用 browser-skill / computer use，而非乱试）。

### 1.6 维护与重构

* 每条新增内容都问一次：**这条信息值得在每一次任务里占用注意力吗？** 答案否定 → 交给代码、独立文档、Skills、Hooks 或按需加载机制。
* 定期删。精简的意义不只是省 Token，更是管理注意力和指令预算。
* 重构提示词（直接粘贴给 Agent）：

```txt
我希望你按照渐进式披露原则重构我的 AGENTS.md 文件。

请遵循以下步骤：

1. **找出矛盾**：识别所有相互冲突的指令。对于每一条矛盾，询问我希望保留哪个版本。

2. **识别核心内容**：只提取应属于根目录 AGENTS.md 的内容：
   - 一句话的项目描述
   - 包管理器（如果不是 npm）
   - 非标准的构建/类型检查命令
   - 与每个任务都真正相关的内容

3. **归组其余内容**：将剩余指令按逻辑类别组织（例如 TypeScript 约定、测试模式、API 设计、Git 工作流）。为每个类别创建独立的 markdown 文件。

4. **创建文件结构**：输出：
   - 一个极简的根 AGENTS.md，其中包含指向各独立文件的 markdown 链接
   - 每个独立文件及其相关指令
   - 建议的 docs/ 目录结构

5. **标记应删除的内容**：识别以下指令：
   - 冗余的（智能体已经知道的内容）
   - 过于模糊、无法执行的
   - 过于显而易见的（如"写出干净的代码"）
```

### 1.7 兼容性

Claude Code 用 `CLAUDE.md`，可用符号链接统一：`ln -s AGENTS.md CLAUDE.md`。

## 2. Token 成本控制习惯

核心公式：

```text
更低成本 = 更少重复上下文 + 更合理模型路由 + 更精准代码检索 + 更清晰 Agent 分工
```

### 2.1 会话与沟通纪律

1. **一个 Session 处理一件事**：修 Bug、重构、写文章、查线上各开一个。Session 越长 → 每轮越贵；Topic 切分是最便宜的 Context 管理。
2. **意图一次说完**：对话式拆碎的每一轮来回都重新组装上下文；四轮对话的成本常是一次完整表达的好几倍。
3. **引用文件带完整路径（`@路径`）**，不要只写文件名让 Agent 去搜。
4. **主动压缩的判断自己下**：自动压缩只解决容量；阶段完成、决策收敛时主动 `/compact`。跨阶段交接用 `/handoff`。
5. **直接给结论 + 指定输出格式**：只要 diff / 步骤 / 结论 / 表格 / JSON，直接要求。输出更短 + 结果更可用 → 重试更少。
6. **CLI 优先于 MCP**：CLI 能解决 → CLI；脚本能解决 → 脚本；最后才 MCP。MCP 的价值在于跨系统编排、结构化返回、权限统一收敛、内部业务能力包装。
7. **模型路由落实到执行单元**，不只在主对话框的心智里（见 2.2）。
8. **便宜模型先跑，需要时升级**：先分类 / 初筛 / 摘要，再交强模型推理。级联工作流让贵模型花在刀刃上。

### 2.2 模型路由与分档

Skill 绑模型（`SKILL.md` frontmatter）：

```yaml
---
context: fork
model: gpt-5.6-luna
---
```

* `model`：指定该 Skill 使用的模型；低复杂度 Skill（单测、commit、格式修复、样板代码）绑便宜模型。
* `context: fork`：任务边界清晰的固定流程放独立执行上下文，不带主会话全部历史。

Agent 分档：Planner → 中高档；Coder → 中档/便宜；Reviewer → 强。

| 任务          | 模型档位      | 理由       |
| ----------- | --------- | -------- |
| 架构设计        | 强         | 长链路推理    |
| 复杂 Bug 分析   | 强         | 多步假设和验证  |
| Code Review | 中高档       | 需要语义理解   |
| 写单元测试       | 便宜        | 模式稳定、模板化 |
| 写 commit    | 便宜        | 输出短、风险低  |
| 批量分类 / 摘要   | 低价或 Batch | 规模大、成本敏感 |

### 2.3 评估与审阅技巧

* **评估**（让 AI 推理项目代码时）：禁止联网搜索、禁止外部工具、不依据此前对话或长期记忆，单纯依靠实现代码推理。
* **审阅**：先速读审阅建议，判断问题是否真实存在；真实存在才修改。改完追加："已根据建议对方案进行调整，再次审阅""已经按照方案实现效果，对结果进行审阅"。

### 2.4 行动清单

**今天就能做**：`/new` 切任务；长会话及时 `/compact`；指定输出格式；清点低频 Skill/MCP（卸掉或按需加载）；能 CLI 先 CLI；引用带 `@路径`；意图一次说完。

**这周能做**：按任务给模型分档；给常用 Skill/Agent/命令绑默认模型；装 RTK 压高频命令输出（本机已完成）；评估 Graphify 或 CodeGraph 让 Agent 知道该读哪里。

**这个月能做**：稳定前缀促缓存命中；评估 headroom / context-mode；建代码图谱、Summary、Memory 外置记忆层；worktree 隔离并发改动；多 Agent 工作流拆分（规划/实现/验证/Review）；Orchestrator-Worker 模式；`.agent/` 目录约定（结构化 JSON 传数据 + progress.json 追踪进度）；Token/成本/重试率/工具调用数观测面板。

### 2.5 补充

* 浏览器相关直接用 computer use 或 browser-skill。
* 私有数据接 MCP 即可让 Agent 访问（"物理外挂"）。

## 3. 多 Agent 协作

### 3.1 为什么单 Agent 越用越贵

规划、写码、测试、Review 全在一个会话 → 上下文越积越长 → 所有任务用同一个模型配置。**职责越混，上下文越胖，成本越高。**

### 3.2 四种手段，别混用

| 手段         | 解决什么   | 历史处理     | 代码改动            | 适用场景     |
| ---------- | ------ | -------- | --------------- | -------- |
| `/new`     | 切断无关任务 | 开新会话     | 同一仓库            | 换话题、换需求  |
| `/compact` | 压长会话历史 | 保留摘要     | 当前工作区           | 长任务续做    |
| subagent   | 拆子任务   | 只给需要的上下文 | 默认不隔离           | 搜索、分析、验证 |
| worktree   | 隔离并发改动 | 不是重点     | 独立 git worktree | 多任务并行开发  |

### 3.3 subagent

* 每个 subagent 独立上下文边界：只看到自己需要的内容，主 session 只看到结果。
* 前提是子任务真能拆开；若每个 Agent 都要重复读同一批背景，拆得越多越贵。
* 典型分工：主 session（规划 + 决策）→ subagent A 影响分析（只看图谱）/ B 写实现（只看相关文件）/ C 跑测试生成报告。
* subagent 可单独绑便宜模型：规划用强模型，执行用便宜模型，互不干扰。

### 3.4 worktree 并发

适用：互相独立的 Bug 修复（5 个不相关 Bug 并行）、并行跑不同重构方案对比、同时生成多个文档。每个 Agent 在隔离 worktree 工作，改不同文件互不冲突。worktree 无改动自动清理；有改动返回路径和分支名，人工 review 后合并。

### 3.5 Orchestrator-Worker 模式

**本质**：让每个 Agent 只看和当前步骤相关的内容，而不是把整个任务的背景塞进每一次调用。

| 角色                      | 职责                              |
| ----------------------- | ------------------------------- |
| Orchestrator（强模型）       | 规划、拆解、调度、汇总；不亲自读大量文件、不亲自跑命令；只决策 |
| Worker（便宜模型，如 DeepSeek） | 每个只做一件事；只看自己需要的上下文；完成即销毁        |

典型成本对比（文章估算）：单 Agent 每轮 215K tokens × N 轮；O+W 每轮 10–14K tokens，压缩 5–10 倍。端到端示例（Go API 层重构）估算 800K–1.2M → 100K–150K tokens，省 70–85%。

**四个设计原则**：

1. **输出结构化**：Agent 间用 JSON 文件传递（自然语言易歧义、难定位）。下游只读关心的字段。
2. **进度文件追踪状态**：`.agent/progress.json` 记录每步 status/worker/output\_file/completed\_at；Orchestrator 每次唤醒只读这一个文件，不回放任何会话历史。
3. **每个 Worker 的 context 包精心裁剪**：派遣指令明确"只读哪些文件、输出到哪里、约束是什么"（约 150 tokens 的指令换最小必要上下文）。
4. **临时文件及时清理**：`.agent/` 是临时工作区，任务完成后 `mv .agent/ .agent-archive/<task-id>/` 或删除，避免旧任务上下文污染新任务。

**数据流转示例**：

```text
Agent A 完成 → 写 .agent/step1_result.json → 上下文销毁
Agent B 开始 → 读 .agent/step1_result.json → 写 .agent/step2_result.json
```

**并行**：独立子任务同时启动。实测加速：2 个 → 1.5–1.8x；3 个 → 2.2–2.6x；4 个 → 2.8–3.4x。

✅ 适合并行：不同模块 Bug 修复（文件无交集）；代码 + 测试 + 文档同时生成；多文件格式化/重构（无依赖）；影响分析 + 实现方案设计。
❌ 不适合：有顺序依赖的步骤；修改同一文件的多个任务；依赖上一步输出的任务。

**在 omp 中的落地**：主会话用 Agent tool 分发子任务（一次调用发多个并行指令）；共享文件用 `local://` 或 `.agent/` 目录；无需自建 Orchestrator 框架。

## 4. 上下文与检索工具

> 每个工具给出：作用 → 安装 → 接入 omp → 验证。⚠️ 为 2026-08-22 核验出的修正。

### 4.1 RTK — 命令输出压缩（已装 ✓）

* **作用**：过滤终端输出的注释、空行、ANSI 码、进度条、重复告警，压"命令输出送往上下文"的量。透明过滤，无感知。
* **安装**（macOS）：`brew install rtk` ✓（本机 0.45.0，等于最新 release v0.45.0）。
* **接入 omp**：⚠️ 文章中的 `rtk init -g --agent omp` **不存在**。当前 0.45.0 支持 `--agent claude|cursor|windsurf|cline|kilocode|antigravity|kimi|pi|hermes|droid|vibe` 及 `--codex`/`--copilot`/`--opencode`/`--gemini` 旗标；`--agent pi` 写入 `~/.pi/`，不覆盖 omp。**omp 的有效路线是 AGENTS.md 指令层**：在全局 AGENTS.md 中声明"shell 命令以 `rtk` 为前缀"，Agent 即自动走 RTK（本机已部署，见 `~/.config/.agents/AGENTS.md` 引用 `~/.codex/RTK.md`）。Codex CLI 用 `rtk init -g --codex`（幂等）。
* **验证**：`rtk gain`（本机实测 185 条命令、省 35.8K tokens ≈ 19.9%）；`rtk gain --history`；`rtk discover`（扫描未覆盖命令）。
* **使用**：`rtk git status`、`rtk cargo test`、`rtk proxy <cmd>`（直通不过滤）。
* **注意**：命令不存在可能是装了同名的 Rust Type Kit，需卸载重装。

### 4.2 Caveman — 回复压缩（未装，按需）

* **作用**：压缩 AI 回复（输出 Token），平均省 65–75%。四档：lite / 默认 full / ultra / wenyan。`/caveman` 激活，`stop caveman` 关闭。
* ⚠️ **核验**：studyzy/caveman fork 存在（2026-07-06 活跃），`install.sh` 存在，但 fork 内容与上游 JuliusBrussee/caveman 一致，**未发现 omp 专用产物**，"fork 版支持 omp"无法核验。omp 下若要使用，手工把 `commands/caveman*.md` 放入 `~/.omp/agent/commands/`，或先跳过该工具。
* **注意**：激进 brevity 提示词已被证实可能损害推理/编码质量（context-mode 官方引 kimi-k2.5 案例）；优先用"指定输出格式"约束，效果不够再加 Caveman。

### 4.3 headroom — 全量上下文压缩（未装，按需）

* **作用**：压所有进上下文的内容（文件、工具返回值、会话历史）；可逆压缩（CCR）原始数据留本地按需取回；含 CacheAligner（稳定前缀促缓存命中）、ContentRouter（按类型分流）。
* **安装**：`pip install "headroom-ai[all]"` ✓（PyPI 0.36.4）。
* **接入 omp**：`headroom wrap omp` ✓（官方 wrap 支持列表明确含 omp）；推荐加 `--memory --code-graph`；撤销 `headroom unwrap omp`。
* **MCP 模式**：`headroom mcp install`，注册 `headroom_compress` / `headroom_retrieve` / `headroom_stats` 三工具。
* ⚠️ **数字更新**：官方当前口径为 JSON 数据 60–95%、coding agent 15–20%（文章称 47–92%，同量级）。

### 4.4 context-mode — MCP 输出压缩 + 会话连续性（未装，按需）

* **作用**：① 沙箱化 MCP 工具输出（Playwright 快照 56KB → 压缩约 98%，315KB→5.4KB）；② 跨 `/compact` 会话连续性（本地 SQLite + FTS5，压缩后只检索相关事件）；③ `ctx_execute()` 用代码代替读文件；④ 不干预输出风格。

* ⚠️ **接入路径更新**（文章写的是 MCP-only 旧路径，仍有效但合规率低）：

  | 路径             | 命令                                                                                                                                              | 路由合规           |
  | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
  | **插件（推荐）**     | `omp plugin install context-mode` → 重启 → `omp plugin doctor`                                                                                    | \~98%，自动注册 MCP |
  | MCP-only（文章路径） | `npm install -g context-mode` + `~/.omp/agent/mcp.json` 配 `{"command":"context-mode"}` + `cp configs/omp/SYSTEM.md ~/.omp/agent/SYSTEM.md` → 重启 | \~60%          |

### 4.5 Graphify — 静态代码图谱（未装，与 CodeGraph 二选一）

### 4.6 CodeGraph — 持久化图数据库（未装，与 Graphify 二选一）

## 5. Herdr 操作（已装 ✓ 0.8.0）

### 5.1 心智模型（按此顺序理解）

1. **会话（Session）**——持久运行的后台服务器。
2. **工作区（Workspace）**——项目级容器，通常对应一个仓库。
3. **标签页（Tab）**——工作区内的一套窗格布局（agent / server / logs）。
4. **窗格（Pane）**——真实终端进程；客户端分离后仍继续运行。
5. **智能体（Agent）**——Herdr 在窗格中识别出的 AI 编码智能体进程。

三种操作模式：**终端模式**（按键直发聚焦终端）、**前缀模式**（`Ctrl+B` 后按操作键）、**导航模式**（持续导航界面）。

### 5.2 智能体五状态

`working`（处理中）| `blocked`（等批准/回答）| `done`（后台任务完成，标签页未查看）| `idle`（可接收新输入且已查看）| `unknown`（已识别但无法判断状态）。

### 5.3 操作要点

* **鼠标优先**：单击聚焦；右键创建/分屏/重命名/关闭；拖动分隔线调大小；终端内拖选复制。无需预配快捷键。
* **最小键盘集**（以 `prefix+?` 实际显示为准）：`?` 快捷键帮助、`c` 新标签页、`v` 右分屏、`-` 下分屏、`h/j/k/l` 窗格移动、`w` 工作区导航、`z` 缩放、`x` 关窗格、`q` 分离客户端。
* **启动智能体**：新窗格直接运行 `omp`，Herdr 自动检测；OMP 集成已安装（`~/.omp/agent/extensions/herdr-omp-agent-state.ts`），新启动的 omp 进程会上报语义化状态。
* **分离 ≠ 停止**：`prefix+q` 或直接关终端窗口，后台服务器、窗格、开发服务器继续运行；外部普通终端跑 `herdr` 重连。**不要在 Herdr 窗格内跑 `herdr`**（主动阻止嵌套）。
* **停止**：`herdr server stop` 终止服务器及窗格进程；可恢复布局与受支持集成的会话，但普通命令、开发服务器等任意进程都已终止。

### 5.4 诊断命令

```bash
herdr status; herdr status server; herdr status client
herdr agent list; herdr agent explain <name-or-pane-id> --json
herdr integration status
herdr --default-config        # 查看默认配置；建议保留默认
herdr server reload-config
```

⚠️ 日志位置核验修正：实际为 `~/.config/herdr/herdr-client.log` 与 `~/.config/herdr/herdr-server.log`（文章另列 `herdr.log`，本机不存在）；配置文件 `~/.config/herdr/config.toml` 现已存在（文章撰写时为空是正常状态）。

### 5.5 60 秒演练（装后或升级后做一次）

`prefix+?` 看帮助 → `prefix+v` 建右侧分屏 → 新窗格 `pwd` → 鼠标切换窗格 → `prefix+q` 分离 → 普通终端 `herdr` 重连。

### 5.6 多 Agent 沟通

* 用 `herdr` CLI 与其它窗格里的 Agent 通信（`herdr --skill` 打印当前版本 skill 原文，是权威参考）。
* 本仓库已有 `herdr` 技能（`~/.agents/skills/herdr`，healthy），可直接让 Agent 用 herdr 管理窗格。

## 6. Review SOP

### 6.1 依据（已核验）

《When Can LLMs Actually Correct Their Own Mistakes?》（arXiv 2406.01297，Kamoi et al.，TACL 2024）：没有可靠外部反馈（测试结果、工具输出）时，模型仅靠自我反思很难稳定纠正错误。**Review 的价值 = 新增上下文信息**（新方法论或额外信息），让 Agent 获得新的注意力方向和额外计算预算。

### 6.2 四种 Review 提示

1. 无信息："检查一下有没有问题。"（价值最低）
2. 有方法："站在反方立场，尝试找出导致方案失败的条件。"
3. 有风险先验："重点检查{并发、状态恢复、边界条件、测试污染}。"
4. 有外部证据：Requirements + diff + tests + lint + typecheck + logs + benchmark，让模型基于真实反馈判断。

### 6.3 质量模型与 SOP

```text
Review Quality ≈ Reviewer Capability（强模型）× Risk Prior（反方立场）×
                  Verification Signal（tests/tools）× Independence（新会话 + 换模型）
```

SOP：

1. 收到需求，Codex + 强模型生成方案。
2. 新开一个会话，对方案 Review（换模型，保证独立性）。
3. omp + 便宜模型执行具体方案。
4. 新开会话修复具体问题，**一个 Bug 一个 Session**。
