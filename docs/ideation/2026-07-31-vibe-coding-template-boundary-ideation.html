Grounding Context

两篇文章的核心要求是同时建立上下文闭环与执行闭环。模板必须让冷启动 Agent 找到项目事实、过程、状态和经验，也必须让验证、门禁、清理与回退成为可观察机制。文章同时明确：目录树不应固定，状态机不是唯一表达，能力分发属于 Plugin/工具包层。

当前仓库已删除前后端业务模板，但仍保留约 1300 行中央 CLI、9 组命令、43 个预装 Skills 和项目内运行时。它已经从全栈脚手架退成 Overlay，却仍管理开发生命周期，和“模板是产品主体”的新约束冲突。

判断标准：工具只能帮助模板资产发挥作用；一旦开始生成需求、裁决方案、推进阶段或拼装应用，它就越过模板边界。

Ranked Ideas

IDEA 1 · RECOMMENDED

证据驱动的可执行模板

95%

产品只发布仓库模板。模板除 Markdown 资产外，包含少量项目本地 Hooks 与确定性检查脚本，用文档、Source Register、用户确认引用、验证报告、清理记录和回退记录判断当前是否具备推进资格。删除 npm CLI、中央文档生成器和常驻复制运行时。

Axis
上下文闭环 + 执行闭环
Basis
direct: 两篇文章都要求 Rules、Skills、Hooks/脚本各司其职，并强调阶段门禁必须由文档、状态与用户证据共同支撑；真实用户路径仍需运行。
Rationale
静态文件恢复上下文，项目本地检查提供短反馈回路；两者同时存在，符合文章的“双闭环”，又没有中央脚手架。
Downsides
需要谨慎设计证据谓词；检查只能证明证据齐全，不能替代真实产品验收。
Complexity
Medium
IDEA 2

纯静态仓库模板

80%

保留 AGENTS.md、workflow/、SPECS/、tasks/、memory/、rules/ 和少量示例，作为 GitHub Template 或可下载目录发布。删除全部 CLI、状态推进命令、路由命令和项目运行时。

Axis
目标项目自主权 + 维护复杂度
Basis
external: GitHub 官方模板模型只负责生成新仓库，生成结果与模板历史无关；这与“安装后项目完全自治”的目标一致。
Rationale
产品边界最清楚，维护面最小，Everything as Code 最直接。
Downsides
现有项目接入、模板升级和冲突处理全部靠人工；执行闭环容易退化为文本建议。
Complexity
Low
IDEA 3

最小核心模板 + 可选能力包

76%

默认模板只保留“新会话六问”、Source Register、决策谱系和验证接口。严格门禁、团队协作、安全、Web E2E 等以独立静态 Profile 或 Agent Plugin 提供，用户显式选择，禁止按技术栈或业务问答自动生成应用。

Axis
模板扩展性 + 上下文信噪比
Basis
direct: 文章要求 AGENTS 只做索引、规则按场景加载、不为无关规则付 token；当前项目却预装 43 个 Skills、约 8.5 MB。
Rationale
不同项目只携带相关能力，核心稳定，外围可以长期复利。
Downsides
能力包组合、版本兼容和选择成本会增长；管理失控后会重新演变成脚手架平台。
Complexity
Medium–High

Rejection Summary

候选淘汰理由
一次性 Overlay 复制没有升级和冲突模型，复制后立即产生版本碎片。
版本化 Overlay 管理器需要 manifest、三方合并和迁移，实质是在重造模板生命周期平台，偏离当前收缩目标。
Plugin-first适合分发通用能力，但无法替代仓库内的项目事实与历史，并产生平台锁定。
中央硬状态机门禁有效，但把一种方法论固化成产品运行时，个人 vibe coding 负担过重。
仅文件命名门禁能表达阶段，不能证明来源、真实验证、清理与回退证据存在。
Git upstream 模板分支用户操作成本高，根目录资产冲突多，不适合作为默认体验。
声明式工作区编译器引入第二事实源和生成器，重新走回脚手架。
